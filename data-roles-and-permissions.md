# Starkeep — Data, Roles, & Permissions Overview

This document describes the system-level stance on roles, permissions, and trust boundaries in Starkeep's cloud deployment. It is intentionally high-level: it covers _who can do what, where the lines are drawn, and why_ — but not the specific IAM actions, PG grants, or policy JSON. Those live in code and in the package-level READMEs.

---

## Two classes of user data

Starkeep operates on two classes of data: "Shared data" is your content (photos, documents, etc) and it's "shared" in the sense that it can be accessed and operated on by multiple apps. "App-specific data" is other app-bound data that is operated on by specific apps, but which is also synced through the Starkeep system. These They are owned by different parties, touched by different identities, and carry different attribution guarantees — so the trust model only makes sense once they are separated.

- **Shared data** is the _user's_ content (photos, documents): typed against a platform-owned registry and stored in the single `shared.records` table plus the `shared/<userId>/<category>/*` object-storage prefix. It is **cross-app and platform-owned** — multiple apps can hold grants on the same type, items outlive the uninstall of any app that touched them, and no app _owns_ shared data. An app is a tenant with declared, narrow access: it reaches only the categories/types its manifest was granted.

- **App-specific data** is an _app's_ own private state (a photo caption, a tag taxonomy, layout preferences): stored in the app's namespaced schema (`app_<appId>.*`) and filespace (`apps/<appId>/<userId>/syncable/*`). It is **per-app and app-owned** — invisible to every other app, and torn down when the app is uninstalled at a location. It never interoperates across apps.

These are handled differently at the identity layer, and that difference is the source of most of the nuance below:

|                                                         | Shared data                                                                                                 | App-specific data                                                                                |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **Owner**                                               | the user (platform-managed)                                                                                 | the app                                                                                          |
| **Who may touch it**                                    | any app with a grant on the type                                                                            | only the owning app                                                                              |
| **Runtime read/write identity** (per-request `/data/*`) | the **calling app's** per-app role, assumed per request by the broker                                       | the **calling app's** per-app role                                                               |
| **Sync write identity** (cloud side)                    | the single **Starkeep Drive** (User-Data-Owner) role, on one always-on channel                              | the app's **own** per-app role, on the app's own channel — only while the app is cloud-installed |
| **Attribution of authorship**                           | IAM-enforced on the runtime path; on the sync path, carried by the immutable `origin_app_id` data attribute | IAM-enforced — the row lives in the app's own schema/prefix                                      |
| **Survives uninstall**                                  | yes                                                                                                         | no (at that location)                                                                            |

Two consequences are worth stating up front, because the principles below lean on them:

- **Shared data has two distinct cloud write paths with different identity models.** A direct, per-request write — an app POSTing a record on `/data/*` — runs under the _calling app's_ per-app role and is therefore IAM-attributable to that app. Background **sync** of shared records instead flows through the single Starkeep Drive channel under `app-starkeep-drive-role`; there, per-app authorship is preserved as the immutable `origin_app_id` attribute (set once at local creation), _not_ proven by the writing IAM principal. Routing all shared sync through one always-on Drive identity is deliberate: shared data always has an authorized cloud writer regardless of which apps happen to be installed, and a record's origin app need not be cloud-installed for its data to sync.

- **For shared data, the enforced property is _confinement to granted types_, not sole-identity ownership.** Because many apps legitimately operate on the same items, "one owner per byte" is not the guarantee. What the system guarantees is that an app can only read or write the types its manifest declares — checked before a sync write ever leaves the device (the local-data-server's `appCanWrite` check) and bounded again in the cloud by IAM (a per-app role's category-scoped grants on the runtime path; Drive's per-user shared ceiling on the sync path). App-specific data, by contrast, _is_ sole-identity owned: it lives in the app's own schema and prefix, reachable by no other role.

- **A `read` grant is no longer write-inert.** An app holding only `read` on a type may write **cross-app labels** on records of that type, into its own server-set namespace in `shared.record_labels`. The confinement claim above is unchanged — the app is still confined to the types its manifest declares, and it still cannot touch the record row, its bytes, or another app's label namespace. But "read means you cause no shared-plane write" was true before and is not now, and that is worth stating plainly rather than leaving a reader to infer it.

  The trade was deliberate: requiring `readwrite` to label would force an OCR service or a classifier to hold **destructive power over records it only ever reads**, which is a strictly worse security posture than letting it append a namespaced, quota-bounded, advisory row. A third grant level between `read` and `readwrite` would express this more literally; it was considered and rejected as more machinery than the distinction earns. What bounds the new power is elsewhere: the namespace is server-set so it cannot be forged, the keys must be declared in the manifest and are capped per app, and values are capped at 128 bytes.

### One deployment, many users

Both classes belong to one user. A deployment serves every account in `starkeep-users` (see "Accounts and groups"), and each account's shared data and app-specific data form a library of its own. Nothing is shared between users: not records, labels, metadata, availability, app rows or bytes.

- **Every row names its owner.** Every owned cloud table — `shared.records`, `shared.record_labels`, `shared.object_availability`, the metadata tables, and every table in an app's schema — leads its primary key with `user_id`. Two users holding one file hold one content-addressed record id each, as two rows.
- **Every object key names its owner.** `shared/<userId>/...` and `apps/<appId>/<userId>/syncable/...`, on every node and in S3. A node's library carries the placeholder `local` until a cloud binds it to a user.
- **Every request acts for one user.** The cloud-data-server takes the user from the request — the ID token's `sub` — and every database statement and every S3 session it issues is that user's alone. See "How data access actually flows at runtime".

## Stance

Three principles drive every choice below.

1. **User data stays confined to the identities authorized for it.** A buggy or hostile app cannot reach data outside its grants — neither another app's app-specific data, nor shared types it was not granted — including via the human admin's own session. No user reaches another user's data, through any app, any device or the admin's own session. How this is _guaranteed_ differs by data class (see above): app-specific data is sole-identity owned (it lives in the app's own schema/prefix, reachable only by the app's role), while shared data is **type-confined** at every layer, with authorship attributed by IAM on the runtime path and by the `origin_app_id` attribute on the sync path. This is the load-bearing security property; everything else exists to make it true.
2. **Powerful permissions are centralized, bounded, and ephemeral.** No identity holds standing power broader than what its job requires at steady state. Dangerous capabilities (DB admin, IAM mint, foundational provisioning) live on dedicated identities that the rest of the system delegates to for a specific purpose and short duration.
3. **Authorization is layered, as nested ceilings.** IAM, Postgres roles + GRANTs, and an application-layer check on the shared records table each constrain access, and any single layer being missed or bypassed is bounded by the next. They are deliberately _not_ three copies of one rule: IAM S3 scoping and PG metadata-table GRANTs are **category-granular** (per `<category>`), while the application-layer check on `shared.records` is **type-granular** (per `<category>/<format>` id — the exact set the manifest declared). The coarser layers are the outer ceiling; the application layer makes the exact cut that DSQL's lack of row-level security would otherwise leave open.

   The cut between users is layered the same way, with one difference. In S3, IAM scopes every per-app session to the user its `starkeep:userId` session tag names, under the cloud-data-server's own key checks. In the database it is application-layer only: DSQL has no row-level security, and a session tag does not change the Postgres role. One compiler plugin makes that cut on every statement, and a tripwire refuses any statement that goes around it (see "How data access actually flows at runtime").

A consequence of (1) and (2): the human admin user is not a superuser. The admin app facilitates deployment and install/uninstall; it has no standing access to _shared_ user data. Its standing grants are limited to driving deployment (Cognito, assume Manager), reading the billing/cost-report bucket, its own `apps/admin/*` app-private prefix, and `dsql:DbConnect` — which maps it to the `${stackPrefix}_installer` Postgres role used to drive the app registry and install-step ledger, a role that holds no grants on `shared.records`. To touch app or shared data, work flows through a chain of role assumptions that each carries the originating app's identity.

## The foundational building blocks

These are the named identities and policies the rest of the system composes from. All are created once, by the bootstrap, and live for the lifetime of the deployment.

### Accounts and groups

Two Cognito groups define an account. An account may be in either or both.

- **`starkeep-admins`** administers the deployment: users, cloud apps, settings and the cloud data server. Only its members get credentials from the identity pool, and admin-web refuses anyone else at sign-in. Membership is what makes someone an admin.
- **`starkeep-users`** has a data library that syncs. The cloud data server checks it on every data call: the HMAC branch, the device-token branch and the mobile branch all read `cognito:groups` from the ID token.

Four Cognito app clients issue the pool's tokens. A client decides what a token from it can do on its own. Only two surfaces ever collect a password: admin-web, which is platform code on the operator's machine, and Cognito's managed login page.

- **The admin client** (`${StackPrefix}-admin`, bootstrap) serves admin-web alone. The identity pool trusts it, so an admin's token from it becomes admin-app credentials. Nothing on the data plane accepts its tokens.
- **The device client** (`${StackPrefix}-devices`, bootstrap) serves desktops, through the local data server, signed in with admin-web's "This machine" form. Its tokens alone admit a signed-in desktop on the cloud data server's device-token branch (see "A device's credential"). It has no OAuth flow, so no phone app can obtain a device token without the password. It issues fifteen-minute ID tokens and ten-year refresh tokens, with token revocation on.
- **The cloud-apps client** (`${StackPrefix}-cloud-apps`, cloud data server install) serves every cloud app's session. A person signs in on the managed login page; the broker's `/auth/callback` exchanges the code with PKCE and sets the app's `HttpOnly` cookies, so app code receives tokens and never a password (see "A cloud app's session"). The HMAC branch, the session authorizer and the gateway's JWT authorizer accept only its tokens. Thirty-day refresh tokens.
- **The mobile-apps client** (`${StackPrefix}-mobile-apps`, cloud data server install) serves mobile apps, which sign in on the managed login page in the system browser. Its tokens pass only on the mobile branch, with a signature by a key attested to an app (see "A mobile app's credential"). Each mobile build's callback (`<scheme>://auth/callback`) is added at the app's registration and removed with it. Fifteen-minute ID tokens and ten-year refresh tokens, with token revocation on.

The identity pool trusts the admin client alone, so a device, cloud-app or mobile token reaches no AWS role. The cloud-apps and mobile-apps clients live outside CloudFormation, because their callbacks name the CloudFront domain and the installed apps; the admin-app role creates and updates them, and teardown removes them with the pool. The pool's managed login domain (`${StackPrefix}-${AWS::AccountId}.auth.<region>.amazoncognito.com`) is a bootstrap resource.

The cloud data server admits any account in `starkeep-users` to its own library; being an admin grants no data. A member uses the deployment's cloud apps and signs in on their own devices, but gets no AWS credentials and cannot sign in to admin-web. Admin-web creates accounts with `AdminCreateUser`, which emails a temporary password; there is no self-service sign-up. "Sign out all devices" ends every sign-in an account holds without disabling it, and disabling an account signs it out everywhere too.

### Identities

- **Admin app role.** The federated entry point. A human in the `starkeep-admins` Cognito group logs in via Cognito and assumes this role; the identity pool maps that group to this role by rule, with `AmbiguousRoleResolution: Deny` and no default role, so any other user gets no AWS credentials at all. See "Accounts and groups" below. It has the operational permissions needed to drive deployment and install/uninstall: talk to Cognito, assume Manager, read/write its own `apps/admin/*` files prefix, read the billing/cost-report bucket, manage the Pulumi state-encryption passphrase parameter, and `dsql:DbConnect` (mapping to the `${stackPrefix}_installer` Postgres role, which can reach the registry and install-step ledger but holds no grants on `shared.records`). It has **no** standing access to shared user data.
- **Manager role.** The delegation hub. Manager can mint and revoke per-app IAM roles (bounded by the per-app permissions boundary), attach and detach temporary policies on the dedicated install-time roles during install/uninstall, and assume into the per-app roles, the install-ddl role, and the install-infra role. Its standing non-IAM capabilities are two SSM prefixes. It writes (and at uninstall deletes) each app's HMAC signing secret as an SSM SecureString under `/${stackPrefix}/app-creds/*` (write/delete only — Manager never _reads_ the secret). It reads and writes the platform's own non-secret parameters under `/${stackPrefix}/platform/*`: the deployment's settings, which admin-web edits. It has no standing user-data-plane power: no S3, no DSQL connect, no Lambda, no API Gateway. Even during install, the wide provisioning policies are attached to _target_ roles, never to Manager.
- **Install-DDL role.** The only identity in the system that can connect to DSQL as PG admin. It has no standing permissions; Manager attaches a small temporary policy granting DB admin around each install or uninstall and detaches it immediately after. This keeps the most dangerous database capability centralized on a single, IAM-bounded role that exists solely to run install/uninstall DDL. Apps being installed never receive DB admin, even briefly.
- **Install-Infra role.** The only identity that performs install-time AWS provisioning for per-app compute stacks (Lambda admin, log groups, API Gateway integrations/routes, Pulumi state writes, `iam:PassRole` to per-app roles). It has no standing permissions; Manager attaches a per-install temporary policy scoped to a single app's resources around each install or uninstall and detaches it immediately after. This keeps install-time AWS power centralized and ephemeral, so the per-app role's _permanent_ ceiling never has to carry verbs it only needs for seconds.
- **Cloud-data-server role.** The runtime identity of the data broker (see below). Created by Manager during cloud-data-server deployment, bounded by the foundational permissions boundary (not the regular per-app one), and carries the broker capability of assuming any per-app role.
- **Per-app roles** (`...-app-<appId>-role`). One per installed app, minted by Manager at install time. Each is bounded by the per-app permissions boundary and tagged with its app id. The app's Lambda(s) run as this role. The cloud-data-server brokers data calls _as_ this role by assuming it directly.
- **User-Data-Owner role.** The standing cloud-write identity for _all shared-record sync_, owned by the built-in **Starkeep Drive** app (IAM/app id `starkeep-drive`). It is **not** created at bootstrap: bootstrap reserves only its permissions _boundary_ (a managed policy — no awkward empty-trust role), and the `starkeep-drive` app id is reserved in installer code so no third-party app can claim it. The role itself (`...-app-starkeep-drive-role`) is minted by `installDrive` with that boundary and a real trust policy naming the cloud-data-server role, mirroring how cloud-data-server's role is minted with the foundational boundary.

### Permissions boundaries

A permissions boundary is the _ceiling_ on what an identity can do, regardless of what policies are attached to it. Starkeep uses five:

- **Per-app permissions boundary.** Caps every per-app role at exactly its _runtime_ job. Scopes S3 to the app's own prefix (driven by the role's `starkeep:appId` tag) and the shared-data prefix, each narrowed to the user the session's `starkeep:userId` tag names; allows DSQL connect (not admin), and denies all IAM mutation. A session with no user tag — Manager's install and uninstall — reaches the app's own prefix as a whole, for the `.keep` marker and the uninstall cleanup, and no shared data. It does **not** carry install-time AWS verbs (Lambda/Logs/API Gateway admin, Pulumi state writes, PassRole) — those live on install-infra. This is what makes a compromised app, or a buggy temp policy, structurally unable to escape its lane _or_ to perform infrastructure operations.
- **Foundational permissions boundary.** A wider ceiling used only by the cloud-data-server role. Permits the foundational provisioning actions (DSQL cluster admin, S3 bucket admin on the well-known files and billing bucket name patterns, the cost-and-usage-report (CUR) definition API, Lambda/API-Gateway admin scoped to cloud-data-server's own resources, and CloudFront admin for the platform distribution and its URL-signing key material) that the regular per-app boundary intentionally forbids. CloudFront is capped as `cloudfront:*` (a global service whose actions almost all lack resource-level ARNs), but that is only the _ceiling_: the specific verbs are granted by the ephemeral temp-install policy and detached after install, and the signing SecureString is written by Manager (not the CDS role, which stays read-only on SSM). A magic-string check in the installer routes only the cloud-data-server app id to this boundary, so a third-party app cannot opt into it.
- **User-Data-Owner permissions boundary.** A wider-than-per-app ceiling used only by the Starkeep Drive role (`starkeep-drive`). Permits `dsql:DbConnect` (not admin) and S3 read/write/list on the files bucket across one user's shared data (`shared/<userId>/*`, the user the session's tag names) — the layer-2 hard floor for shared-record custody — and nothing else: no Lambda/API Gateway, no per-app schema, no DSQL cluster admin, no IAM mutation. A magic-string check in the installer routes only the `starkeep-drive` app id to this boundary, so a third-party app cannot opt into the cross-category shared ceiling.
- **Install-DDL permissions boundary.** A very narrow ceiling for the install-ddl role: essentially DSQL admin connect plus a defense-in-depth deny on IAM mutations. The install-ddl role cannot do anything else, ever, by construction.
- **Install-Infra permissions boundary.** A narrow ceiling for the install-infra role: the AWS provisioning verbs needed to stand up and tear down a per-app compute stack (Lambda admin, log groups, API Gateway integrations/routes, Pulumi state I/O, PassRole onto per-app roles), plus a defense-in-depth deny on IAM mutations. Per-install scoping to a specific app id is enforced by the temp policy on top, not by the boundary.

### Supporting resources

- **Cognito user pool + identity pool.** Federated login; the identity pool is what maps a logged-in admin to the admin-app role. The pool has the four app clients and the managed login domain described under "Accounts and groups".
- **Pulumi state bucket.** Per-app infrastructure (Lambdas, API Gateway integrations, routes) is provisioned with Pulumi; state lives in a dedicated S3 bucket, encrypted with a passphrase stored as an SSM SecureString.
- **Artifacts bucket.** Holds each app's compiled Lambda bundle (`apps/<appId>/latest/dist.zip`); install-infra uploads here during install and clears the prefix on uninstall. Never holds user data.
- **Pulumi state-encryption passphrase (SSM SecureString).** Not created at bootstrap — CloudFormation cannot create SecureString parameters. The admin-installer mints it (create-if-missing, so it stays stable once any Pulumi state exists) on the first cloud-data-server install.
- **Billing/cost-report bucket.** Receives the AWS cost-and-usage report; provisioned as part of the cloud-data-server foundational install, not at bootstrap.

## The three setup phases

Starkeep stands up in three distinct phases. Each phase has a different security posture, and the boundaries above are what make the transitions safe.

### Phase 1 — Bootstrap (CloudFormation)

A single CloudFormation stack runs in the user's AWS account and creates: the Cognito pools, the admin-app role, the Manager role, the install-ddl role, the install-infra role, all five permissions boundaries (including the User-Data-Owner permissions boundary), the Pulumi state bucket, and the artifacts bucket. The Pulumi state-encryption passphrase is **not** created here — CloudFormation cannot create SecureString SSM parameters, so the admin-installer mints it (create-if-missing) on the first cloud-data-server install. The cloud-data-server's IAM role, the Starkeep Drive (User-Data-Owner) role, the billing bucket, and the data-plane resources do **not** exist yet — Drive's role is minted later by `installDrive`. The User-Data-Owner _boundary_ exists after bootstrap; the _role_ does not.

After this phase, the user can log in and assume the admin-app role. Nothing else in the system has any power, because nothing else exists.

### Phase 2 — Cloud-data-server deployment

The cloud-data-server is treated as a built-in app, but its permissions story is different from third-party apps in two important ways:

1. **Its capability ceiling is set upfront, in the bootstrap, as the foundational permissions boundary.** That boundary is what permits foundational provisioning (creating the DSQL cluster, the files bucket, the protocol-core Lambda, the API Gateway). It does not have to be invented or granted at deploy time.
2. **It does not bring its own manifest in the third-party sense.** It ships with starkeep-core and is deployed by the admin app using the installer plumbing — Manager mints `...-app-cloud-data-server-role` with the foundational boundary, attaches a temporary install policy (wider than per-app temp-install because foundational resources need to be created), runs the cloud-data-server's Pulumi program to create the DSQL cluster, the files bucket, the protocol-core Lambda function, and the shared API Gateway, then detaches the temp policy.

After this phase, the data plane exists. The cloud-data-server's runtime identity has the broker capability — it can assume any `...-app-*` role — but it has no direct access to shared data through its own credentials. Its standing policy is intentionally narrow.

### Phase 3 — App install (per app, repeatable)

Third-party (and additional first-party) apps install via the standard installer pipeline. Each install is an orchestrated sequence of idempotent steps; the orchestrator persists step status so a partial failure can be resumed. A key property of the sequence is that **the two install-time temp policies are never attached at the same time**: each is a tight bracket around exactly the step that needs it, attached just before and detached immediately after, so the wide grants exist for the minimum possible window.

1. **Create the signing credential.** Manager creates the app's HMAC signing secret in its SSM SecureString (`/${stackPrefix}/app-creds/<appId>`), once: the put is create-only, so a reinstall keeps the existing secret. The app's own Lambdas sign with it, and the cloud-data-server verifier reads it to authenticate the app's signed requests. Nothing on the operator's machine signs cloud requests with it, so the cloud install needs no local install.
2. **Mint.** Manager creates the app's per-app role with the per-app (runtime-only) permissions boundary and the `starkeep:appId` tag. From this moment on, every action attributed to the app at runtime is bounded by the per-app boundary. The role is not granted install-time AWS verbs even temporarily.
3. **DDL as install-ddl (DB-admin bracket).** Manager attaches a temp policy on the _install-ddl role_ (DB admin), then a role chain (admin → Manager → install-ddl) connects to DSQL as PG admin and runs the per-app DDL: create the per-app PG role, create the app-private schema, grant the correct read/write/metadata permissions on shared tables based on what the app's manifest declares. Manager detaches the temp DDL policy as soon as the DDL completes — before any infrastructure provisioning begins. The app itself never holds DB admin. (One subtlety: `CREATE SCHEMA … AUTHORIZATION <app-pg-role>` requires the creating session to be able to `SET ROLE` to that target, so install-ddl runs `GRANT "<app-pg-role>" TO admin`. This makes admin a member _of_ the app role, not the other way around — the app role gains no privileges from it, and only install-ddl can reach admin, so the membership is exercised only during install/uninstall. See the comment in `packages/admin-installer/src/dsql-ddl.ts` for the mechanics.)
4. **Seed the app's storage prefix.** Under the freshly minted per-app role (admin → Manager → app role), the orchestrator writes the `apps/<appId>/.keep` marker — exercising the per-app role's own narrow runtime grants, with no temp policy attached.
5. **Provision as install-infra (infra bracket).** For apps with compute, Manager attaches a temp policy on the _install-infra role_ (scoped to this app's Lambda name pattern, its log groups, its Pulumi state file, the artifacts-bucket prefix, and `PassRole` onto its own per-app role). A role chain (admin → Manager → install-infra) uploads the app bundle and runs the app's Pulumi program to create its Lambda(s), log group(s), API Gateway integrations, and routes; the program passes the per-app role to Lambda as the function's execution role. Manager detaches the temp infra policy when provisioning completes. (Compute-less apps — e.g. Starkeep Drive — skip this stage entirely.)
6. **Register.** The app is recorded in the registry with the surfaces this install added. Installing the mobile app records the build's identity (`shared.app_mobile_identities`) in the same transaction as `mobile_app`, and adds its callback to the mobile-apps client. Both install-time roles are back to zero standing permissions; the per-app role retains only its narrow runtime policy.

**Install surfaces.** Steps 1 to 4 and step 6 are an app's _data side_, which every install creates: the data role, its Postgres role and IAM mapping, the `app_<appId>` schema and tables, the namespace row, the `.keep` marker, the grants and the label keys. The data side serves the desktop's sync and every surface. On top of it the operator installs the _web app_, the mobile app, or both (`cli:install-app <appId> --web`, `--mobile`, or neither flag for every surface the manifest offers). The web app adds the exec role and step 5. The mobile app adds the Android identity (`shared.app_mobile_identities`) and its callback on the mobile-apps client. `shared.app_registry` records the two choices in `web_app` and `mobile_app`; a row with both false, as Drive's, is a data side alone. Step 1 runs for every install, because the cloud data server reads the parameter's existence as the app's installed marker, and the signed-in-device branch refuses an app without one. `cli:uninstall-app <appId> --web` or `--mobile` removes that surface's parts, clears its column and keeps the data side.

Uninstall is the symmetric flow, again bracketing each temp policy tightly: Manager attaches a temp uninstall policy on install-infra and runs Pulumi destroy as install-infra, then detaches it; files-bucket prefixes are cleared under the app's own role; Manager attaches a temp DDL policy on install-ddl, revokes grants and drops the PG role and schema as install-ddl, then detaches it; the registry entry is removed; the per-app IAM role is deleted; and the app's SSM signing credential is deleted. Shared records persist for other apps that still have grants.

## How data access actually flows at runtime

Once an app is installed, an end-user request that needs to touch shared data flows like this:

1. The client (browser) reaches the shared API Gateway through the platform-owned CloudFront distribution, calling the **app's own same-origin signing proxy** under `/apps/<appId>/...`, not the data plane directly. CloudFront is an **optimization layer, not a security boundary**: it edge-caches app static assets and passes API calls through to the gateway unchanged (forwarding all viewer headers except `Host`, so JWT and HMAC signatures survive intact). The gateway remains directly reachable — locking it to CloudFront-only access is not part of this design — so all authorization still happens at the gateway/handler exactly as described below; nothing may assume edge-level protection. (Server-to-server HMAC calls skip CloudFront and hit the gateway URL directly.)
2. The app's own compute handler loads its HMAC secret from SSM and re-issues the call to the cloud-data-server's data plane as a **signed server-to-server request**. This hop is why the browser never holds the app credential, and it is also where the end user must be checked — see the boundary note below.
3. The cloud-data-server Lambda verifies the HMAC signature, which identifies the **calling app**, and the end-user ID token that rides with it, which identifies the **user**. It then assumes the per-app role directly for the duration of the request (`...-app-<callerAppId>-role`), tagging the session with `starkeep:userId`. The per-app role's trust policy names the cloud-data-server role as a principal, and lets it set that one session tag and no other, so it cannot override the role's `starkeep:appId` tag. This is a single hop with no Manager in the chain.
4. Under those assumed credentials, the cloud-data-server builds the DSQL and S3 adapters and runs the data operation. DSQL maps the assumed IAM identity to the per-app PG role; S3 calls are bounded by the per-app permissions boundary to the app's allowed prefixes, under the session's user. Every database statement compiles through a compiler scoped to the user (`storage-aurora-dsql/src/owner-scope.ts`): reads, updates and deletes of an owned table gain the user's predicate, inserts are stamped with the user, and the cloud-data-server's database client refuses any statement against an owned table that skipped it.

> **Where the end user is authenticated: in the cloud-data-server, on every data call.**
>
> The data plane carries no gateway JWT authorizer; it was removed on 2026-06-11 (`plan-cloud-auth-foundational-fixes-2026-06-11.md`, step 1), because a gateway-level check said nothing the app's signature did not. Between 2026-05-25 and 2026-08-23 nothing on the data path examined the end user at all, which is the subject of `postmortem-unauthenticated-cloud-apps-2026-08-23.md`.
>
> The cloud-data-server now requires a credential bound to a named user on every data call, with no route exemptions: an app's signed request carries the user's Cognito ID token from the cloud-apps client, which the handler verifies, a signed-in desktop presents its own ID token from the device client, and a mobile app presents a mobile-apps token with its attested key's signature. The user it yields is the user the request acts for — the data group check, the per-user database cut and the session's `starkeep:userId` tag all come from it. An app still authenticates its own end user in its own server code, in the proxy hop at step 2, because the token it forwards is the one it obtained; `createDataProxyHandler` requires an explicit `endUserAuth` decision rather than defaulting to open.

Two consequences are worth calling out:

- **Cloud-data-server is a broker, not a data owner.** Its own credentials never read or write shared data. On the **runtime per-request data path** (reads/writes on `/data/*`), every shared byte is attributable to the per-app role that the broker assumed for that specific request. (The **sync path** is different — see below.)
- **Application-layer enforcement is required for per-type filtering.** All shared records live in a single table (DSQL has no row-level security), so the protocol-core layer reads the caller's grants and applies type-level filters on reads and writes before any query is issued. This is the type-granular cut that the coarser layers leave open: PG GRANTs and the per-app S3 ceiling are category-granular; the application layer handles per-type-in-`shared.records` access.

  **`shared.record_labels` is on the same footing, and its PG GRANTs are correspondingly coarse.** Every per-app PG role holds `SELECT, INSERT, UPDATE, DELETE` on it, exactly as for `shared.records` — the per-app cut is application-layer in both data servers, not in the database. This is not a new weakening; it is the same "DSQL has no RLS, so the app layer is the granular cut" trade, applied to a second table. What the app layer enforces there is a `read` grant on the _record's_ type plus a manifest-declared key, and — the part the database genuinely cannot express — an `app_id` taken from the authenticated subject rather than from the request, which is what makes namespace squatting unrepresentable.

  **`shared.app_label_keys` is world-readable by design** (`GRANT SELECT … TO PUBLIC`, mirroring `shared.access_grants`), writable only by the installer. Which label keys an app publishes is public schema, not user data, and cross-app discoverability is the entire reason keys are declared in a manifest rather than counted at runtime.

The same single-hop assume serves **app-specific** runtime operations, but those target the app's _own_ schema (`app_<appId>.*`) and filespace (`apps/<appId>/<userId>/syncable/*`) rather than `shared.*`. No cross-app visibility arises, and no application-layer type filter is needed — the per-app PG role and permissions boundary already make the app's own namespace the only thing it can reach.

**Drive's bytes watermark is the one deliberate exception** (`GRANT SELECT ON app_starkeep_drive._starkeep_byte_coverage TO PUBLIC`, with `USAGE` on the schema). Every per-app role may read it. The table holds one HLC per device per user and no record content. The cloud-data-server reads it on an app's request to decide whether a shared file has reached S3 before it signs a URL (`cloud-data-server/src/byte-presence.ts`). The owner-scoped compiler confines that read to the request's user, as it does for `shared.records`. Writes stay with Drive's role alone, because a forged watermark would make phones skip uploads. `USAGE` exposes the names of Drive's other tables and none of their rows.

**The node watermark tables mirror their source tables' grants.** Three tables hold the cloud's sync coverage per user and author: `shared.node_watermarks_records` for `shared.records`, `shared.node_watermarks_labels` for `shared.record_labels`, and `app_<appId>._starkeep_node_watermarks` for every synced table in the app's schema (`storage-aurora-dsql/src/node-watermarks.ts`). Each table carries its source table's grants exactly. A per-app role reads `shared.node_watermarks_records` and writes it only where it writes `shared.records`. `PUBLIC` reads and writes `shared.node_watermarks_labels`, as it does `shared.record_labels`. The app's own role alone holds its schema's table. A forged high entry would cause harm: requesters would stop pushing that author's rows, because the cloud would claim it already holds them. Two bounds limit that harm. No app code holds a DSQL connection, so only the cloud-data-server writes these tables. The broker's client refuses every write to them except the canonical raise, which selects its value from rows of the request's user that the same transaction wrote, so a bug can record only a stamp that a real row carries. `DELETE` stays wherever the source table has it, because deleting an entry only lowers coverage and makes requesters re-ship. A new path that hard-deletes synced rows must clear the matching entries, or the cloud would report coverage it no longer has.

**Shared file _bytes_ are served via CloudFront signed URLs, not S3 presigned GETs.** The three shared file-url endpoints (`GET /data/records/:id/file-url`, the batch `POST /data/records/file-urls`, and the shared-prefix `GET /files/{key}/presign`) still run their existing authorization checks (per-type on the record-id routes, per-category on the raw-key route), but they mint a CloudFront signed URL against the platform distribution's `shared/*` behavior instead of presigning S3. This has one deliberate trust consequence: **the per-app IAM ceiling no longer applies to shared _reads_.** The CloudFront signing key is not category-scoped — whatever `shared/*` key the platform code signs, CloudFront serves — so the layered nested-ceiling property (IAM ⊇ PG GRANT ⊇ app-layer check) is reduced on this one path to two ceilings: the **structural** `shared/*` behavior scope (the distribution has no behavior for `apps/*` or any other prefix, and OAC opens the bucket only to the distribution, so the worst case of an app-layer bug is a cross-type or cross-user leak _within shared data_ — never private app files or other buckets) plus the **application-layer grant check**. Because the app-layer check is now the sole per-request line of defense here, all shared-read signing funnels through one **pre-sign revalidation chokepoint** (`signSharedCloudFrontUrl`) that re-parses the key, requires the `shared/` namespace, rejects path traversal, and re-checks the key's user segment against the request's user and its category against the caller's grants immediately before signing — no route reaches the signer around it. The user check is the only per-user cut on this path, for the same reason the category check is the only per-category one. The signing private key lives in an SSM SecureString readable only by the cloud-data-server Lambda role (per-app roles cannot read it), so a malicious app cannot sign URLs itself; it can only call the platform endpoints, which enforce its install-time grants. **Writes and app-data reads are unchanged:** presigned PUT uploads and the `apps/<appId>/<userId>/syncable/*` read path stay on S3 presign and remain fully IAM-bounded, by user as well as by category. If the layering ever needs restoring, the documented escape hatch is per-category key groups or reverting hot categories to S3 presign.

Shared-record **sync** does **not** re-assume per-app roles. It flows through the single always-on **Starkeep Drive (User-Data-Owner)** channel: the local-data-server runs one Drive sync engine that ships all shared records, and the cloud-data-server serves that channel under `app-starkeep-drive-role`. Shared writes are therefore **type-confined locally by the originating app's grants before ship** (the local `appCanWrite` check, layer 1) and **bounded in the cloud by Drive's IAM grant** on the user's `shared/<userId>/*` (layer 2); origin attribution is preserved immutably in `origin_app_id`. There is no per-record role re-assumption and no "origin app uninstalled → rejected" path: a record's origin app need not be cloud-installed for its shared data to sync (that is the whole point of routing shared sync through Drive). Per-app channels carry only that app's _app-specific_ rows and matter only when the app is cloud-installed.

### A cloud app's session

A cloud app's browser session is two `HttpOnly` cookies at the app's mount, `/apps/<appId>`: `sk_session` holds a cloud-apps refresh token and `sk_token` an ID token minted from it. The platform sets them; the app's code never sees a password.

- **`GET /auth/start?app=<appId>&return=<path>`** refuses an app that is not installed, the apps with no browser surface (Drive, the cloud data server), and a return path outside `/apps/<appId>/`. It keeps a PKCE verifier and a `state` in a ten-minute `HttpOnly` cookie at `/auth` and redirects to the managed login page.
- **`GET /auth/callback`** checks `state`, exchanges the code with the verifier, verifies the ID token against the cloud-apps client, sets the two cookies at the named app's mount only, and returns to the checked path. It re-checks the app and path the cookie names, because any app's script on the shared origin can write that cookie.
- **`GET /auth/sign-out?app=<appId>`** clears the app's cookies and ends the managed login session at the domain's `/logout`; `GET /auth/signed-out` returns the browser to the app.

The routes live on the shared origin, so they add no reach beyond what shared-origin script already has (see the plan's "Cloud apps share one origin" risk).

### A device's credential

A desktop that syncs — a computer running the local data server — presents one credential: an ID token from the device client, and nothing else. Phones no longer use the device client; see "A mobile app's credential".

The person signs in with the email and password of the account an admin created, in admin-web's "This machine" section. Only platform code sees the password: admin-web passes it to the local data server, which calls Cognito. A desktop that knows only the cloud's address learns the region, pool and device client from the public `GET /auth/config`. The broker takes the device-token branch for a request that carries `X-Starkeep-User-Token`, no app signature and no `X-Starkeep-Key-Id`, and admits it only when:

- the token's `aud` names the device client. The HMAC branch and both authorizers refuse a device-client token in turn, so a device token is no cloud app session either, and the mobile-apps client's tokens fail here;
- the token's `cognito:groups` includes `starkeep-users`. The fifteen-minute ID token bounds how long a user removed from the group, or disabled, keeps syncing;
- the app has a secret in SSM, and the route and write pass the checks below.

The library binds to the token's `sub`. Revocation is per user: an admin's "Sign out all devices" or "Disable" ends every refresh token the user holds, and a device's own sign-out revokes its refresh token with `RevokeToken`. No single device's session can be revoked alone; `findings-mobile-sign-in-sync-2026-10-10.md`, "Adding per-device revocation later", records how that could return.

- **A desktop acts as Drive or any app installed in the cloud.** The broker refuses an app id with no secret in SSM.
- **A device reaches only the routes its host calls.** A device may call `GET /health`, `GET /deployment/settings`, `POST /sync/exchange`, `POST /files/presign`, `GET /files/<key>/presign`, `GET /files/<key>/stat`, `HEAD /files/<key>`, `GET /data/types` and `GET /data/records`; the last two serve Drive's UI through the local data server's cloud proxy. Every other route is refused, so a stolen device cannot delete records through the record routes.
- **A device never writes the platform's own files.** The broker refuses an exchange that carries a `starkeep/*` record and a presigned upload to a `shared/<userId>/starkeep/` key.
- **A device syncs one user's library.** The broker refuses any key a device names under another user's segment, and a node signed in as a different user than its library's stops syncing (see "The local data server").

### A mobile app's credential

A mobile app signs in on the managed login page in the system browser, through the mobile-apps client with PKCE, and never sees the password. A token says who the person is, but the client is public, so it cannot say which app holds it. The app proves that with Android Key Attestation:

1. **Registration.** After each sign-in the app makes a Keystore key attested with SHA-256 of the new ID token and posts the chain to `POST /apps/starkeep-drive/mobile/keys` with the token. The broker verifies the token against the mobile-apps client and the data group; verifies the chain to Google's attestation roots, pinned in code, and against Google's revocation list; requires a TEE or StrongBox key generated in hardware, EC P-256 for signing, a locked bootloader and a verified or self-signed boot state; requires the challenge to match the token; and maps the attested package and signing certificates to exactly one registered app (`shared.app_mobile_identities`). It stores `{ keyId, userId, appId, publicKey, registeredAt }` at `/<prefix>/platform/mobile-keys/<keyId>`, the one SSM path the cloud-data-server role may write.
2. **Every request.** The app sends the token, `X-Starkeep-Key-Id`, `X-Starkeep-App-Ts` and `X-Starkeep-Key-Sig`: ECDSA P-256 over the message the app HMAC signs, `${appId}:${METHOD}:${path}:${ts}:` and the body. A request naming a key takes the mobile branch and never falls back to another.

The mobile branch admits a request only when the token verifies against the mobile-apps client, the key is registered to the token's `sub`, the signature and timestamp verify, the path is Drive's channel or the attested app's own, the route is on the device allowlist, the write avoids the platform's files, the account is in `starkeep-users`, and the app's mobile app is still installed (its identity row exists exactly while `mobile_app` is true). On Drive's channel it acts **with the attested app's grants, never Drive's**:

- **The exchange is narrowed to the app's readable types.** It runs on an adapter whose compiler adds the type predicate to every read of `shared.records` and of `shared.record_labels` (`storage-aurora-dsql/src/type-scope.ts`), so the rows sent, the coverage watermarks and the digest all describe the same narrowed library and the phone and the cloud agree. The bytes watermark is the channel's, shared with every desktop, so its walk reads the whole library and the reply's value is cut back to the narrowed rows.
- **A push is checked first and refused whole.** Every pushed record must be of a type the app may write, with its file in that type's category; no pushed record may overwrite a row of a type the app may not write; every pushed label must be the app's own, on a declared key, on a record the app may read; and no app-private rows ride the channel.
- **Files and record reads use the app's grants.** Every presign, multipart, stat and record route checks categories and types against the app's grants, so a key in another category is refused.
- **The app's own channel carries its private rows.** A mobile app also reaches `/apps/<attestedAppId>/*` on the same device allowlist, where the broker assumes the app's own data role and runs the per-app exchange in the app's schema, scoped to the token's user, exactly as for the app's cloud compute. Every other app's id is refused. A push on this channel carrying shared records or labels is refused whole in the gate, because the per-app transport would otherwise drop them unread; shared data reaches the cloud through Drive's channel and its checks alone. The channel's file routes reach the app's `apps/<appId>/<userId>/syncable/*` keys, and its record and presign routes check the same grants as on Drive's channel.

Residual risks:

- **A mobile app's identity is only as strong as its signing key.** The attestation names the package and the signing certificates. A build signed with a public key, such as Expo's stock debug keystore, can be imitated by anyone who builds an APK with the same package name.
- **A hostile app can still ask for a password.** Nothing stops an app from drawing its own form, and a typed password signs in through the device client with a desktop's scope. Browser sign-in makes such a form unusual, but closing the path needs a device client that accepts no password.
- **Attested keys accumulate.** Each sign-in registers a new key and nothing deletes old ones. A key without a live token reaches nothing.

## The local data server

The local data server runs outside AWS and holds no AWS credentials. It mediates the local SDK's access to local SQLite + filesystem using the same SDK code paths the cloud uses, so a manifest grant that's wrong (or missing) produces the same denial in dev as in production. It also runs the **layer-1** per-app type check (`appCanWrite` against the local grants) _before_ any record is handed to a sync channel — so a record an app may not write never reaches the cloud in the first place, fully offline.

Every call the local server makes to the cloud carries this machine's sign-in — the device client's ID token (see "A device's credential" above); it holds no app secret for the cloud and no AWS credentials. The session lives in `~/.starkeep/device-session.json` (mode 0600), and the directory is the owner's alone (mode 0700). The sign-in routes refuse any request that carries an `Origin` header, and so does the route that sets the cloud a machine joins: every web page in the person's browser can reach a loopback server, and a hostile one could otherwise sign an unbound machine in to the attacker's account or point it at the attacker's cloud. Admin-web reaches them through its own server, which sends none, and checks that its own requests came from its own page. Both servers listen on `127.0.0.1` and refuse any request whose `Host` is not a loopback name. That check stops DNS rebinding, in which a page on an attacker's domain re-resolves the domain to `127.0.0.1` and sends requests whose `Host` and `Origin` both name the attacker. Admin-web also refuses any write whose `Origin` is present and is not its own. An operator who lists LAN names in `STARKEEP_ADMIN_DEV_ORIGINS` opens admin-web to those names and to the network. A sign-in learns its pool from the joined cloud's `/auth/config` alone, never from pool ids in `config.json`, and refuses an account outside `starkeep-users` before the library binds to it. A sign-out that cannot reach the pool keeps the token and its issuing pool, and the next start or sign-in revokes it there. The local server starts no sync channel until the machine is signed in. Its library belongs to one user. Until then, it writes every key under the placeholder segment `local`; on sign-in it binds the library to the token's `sub`, renaming that segment on disk and in every stored key before the first sync, and from then on a sign-in as a different user leaves sync off rather than mixing two libraries. The phone binds the same way, before its first exchange. For shared data, the local server's only cloud interaction is the **Starkeep Drive channel**, which acts as `starkeep-drive`. There is no per-record role re-assumption on the cloud side: the cloud-side write identity for shared data is **always Drive**. The local server still holds no AWS credentials — it talks to the shared API as the Drive channel, and the cloud-data-server assumes `app-starkeep-drive-role` to perform the write, bounded by Drive's IAM grant (layer 2).

## Why this layout, in one paragraph

The admin user, the platform, and the apps each get exactly the power their job requires and no more. The three most dangerous install-time capabilities — minting IAM roles, connecting to DSQL as DB admin, and provisioning per-app AWS compute infrastructure — are isolated on three different dedicated identities (Manager, install-ddl, install-infra) that have no other powers and are reached only through role chaining. The per-app role's permanent ceiling matches its runtime job exactly, with no install-time verbs sitting on it for the lifetime of the app. The data broker (cloud-data-server) never holds shared-data permissions of its own; it borrows them per-request from the originating app via a direct, single-hop assume. The permissions boundary system means that even if a temp policy has a bug, no role can exceed the ceiling set at bootstrap. And the same SDK code paths run locally and in the cloud, so authorization mistakes surface in the same shape at dev time as in production.
