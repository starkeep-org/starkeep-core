# Admin

The admin panel is the command center for Starkeep. Start here — it guides you through the full setup process and provides ongoing visibility into local and cloud state.

## Running

```bash
pnpm --filter admin-web dev            # hot-reloading, on port 3000
```

For the built client instead of the development one:

```bash
pnpm --filter admin-web build
pnpm --filter admin-web start          # --port <n> to move it
```

## How it is put together

Two halves, joined by `src/server.ts`.

- **The browser half** is a Vite single-page app. `src/main.tsx` mounts it,
  `src/App.tsx` holds the route table, and `vite build` emits `dist/index.html`
  plus content-hashed assets under `dist/_immutable/`.
- **The server half** is a [Hono](https://hono.dev) app. `src/api.ts` is the
  whole `/api/*` route table in one readable list, and each handler lives in its
  own module under `src/routes/`.

`src/server.ts` runs both: it serves `/api/*` from the Hono app and everything
else from the client — Vite in middleware mode under `--dev`, `dist/` otherwise,
with every client route answered by the shell so a reload or a pasted URL
resolves. It runs as TypeScript under `tsx`, the way
`apps/local-data-server` does, because admin-web only ever runs from this
checkout on the operator's own machine.

`src/lib/app-scan.ts`, `src/lib/daemon-control.ts` and
`src/lib/exec-commands.ts` are server-side only: they reach
`node:child_process` and `node:fs`, and nothing the browser loads may import
them. An eslint rule catches the import and
`__tests__/server-module-isolation.test.ts` walks the whole graph.

## What It Does

### Dashboard

The dashboard shows the current state of the local and cloud environments, and is also where you discover, install, and manage apps.

- **Local** — whether the data-server is running, file watches (add/remove watched directories), Drive status, and the list of locally installed apps with install/uninstall and start/stop controls
- **Cloud** — whether cloud infrastructure is provisioned and reachable, cloud sign-in, the list of cloud-installed apps, and a month-to-date / projected cost breakdown
- **App discovery** — manage the parent directories scanned for installable apps; discovered apps are split into Local and Cloud lists based on each manifest's `targets`

### Cloud Setup Wizard

A step-by-step wizard that walks you through provisioning cloud infrastructure for a new user:

1. Enter bootstrap stack outputs (the CloudFormation outputs from the control plane stack)
2. Create a Cognito user account
3. Sign in to verify credentials
4. Deploy the IAM permissions stack
5. Provision the user's full infrastructure (Aurora DSQL, S3, API Gateway, Lambda)

The wizard writes a `starkeep-config.json` file that the data-server reads to connect to the cloud.

### Settings

- **Import/export cloud config** — move configuration between machines or back it up
- **Redeploy infrastructure** — trigger a fresh deployment of the user's cloud stack
- **Reset wizard** — clear config and start the setup process over

### Permissions

Manage the IAM permission stacks that authorize Starkeep to provision and access AWS resources. You can view the IAM statements grouped by component (SST, Aurora DSQL, S3, Lambda, API Gateway, CodeBuild), and create, update, or delete permissions stacks via CloudFormation.

## Configuration

The admin panel reads cloud configuration from `starkeep-config.json`. This file can be:

- Generated by the cloud setup wizard
- Imported manually via the Settings page
- Located at the repo root or pointed to via the `STARKEEP_CONFIG` environment variable

Cognito credentials (for signing in to the user's AWS Cognito pool) are stored in browser localStorage and used to authenticate requests to the data-server and cloud API.
